- Read `scripts/README.md` before choosing project commands, dependencies, or
  environments; it is the project-specific command reference.

## Addy Skill Artifacts

Store artifacts generated by Addy agent-skills under
`docs/initiatives/<initiative-id>/` instead of their default locations.

Use lowercase `kebab-case` for `<initiative-id>`.

## Multi-Agent Workflow

At task intake, the Root uses `using-agent-skills` to select the applicable
Addy Skills. Whenever routing enters Define, the Root invokes `interview-me`
first.

Addy Skills define lifecycle applicability, methodology, quality gates, and
approval requirements. This file defines only project-specific multi-agent
ownership, delegation, candidate integrity, escalation, repository isolation,
and Ship authority.

### Ownership

- **Root:** Define, Plan, approvals, lifecycle transitions, escalation, final
  reporting, Default and Reviewer dispatch, and direct execution of Ship.
- **Default:** Build, Fix, Verify, Re-verify, and verified local commits.
- **Reviewer:** Review and Re-review only.

Changes to requirements, scope, architecture, public interfaces, acceptance
criteria, or release behavior remain Root decisions.

## Delegation

The Root directly creates every Default and Reviewer. Defaults and Reviewers
must not create, trigger, message, or coordinate with other agents.

Every delegation must be self-contained and identify:

- The applicable approved Addy artifacts, if any.
- The assigned checkpoint, task, fix, or review scope.
- Acceptance criteria and verification requirements.
- The exact staged-path allowlist.
- The repositories and submodules in scope.
- The task branch name.
- The applicable repository rules.
- The evidence required in the final report.

For delegations after the first checkpoint, include the recorded original
branch and base HEAD for every repository in scope.

The Root reads the approved Addy plan and task-list artifacts and delegates work
using their explicit checkpoint boundaries. Each checkpoint is assigned to one
fresh Default, which completes its tasks sequentially and returns only after
the checkpoint is complete or a Root escalation is required.

## Default Execution

The Default follows the delegated Addy Skills internally.

Before mutation, the Default performs the repository preflight defined under
Git and Submodules. If unrelated dirty state or unexpected repository state
exists, the Default stops and escalates to the Root. It must not stash, move,
commit, reset, overwrite, or discard unrelated work.

The Default handles ordinary implementation and verification failures without
reporting intermediate progress to the Root.

Before committing a task candidate, the Default:

1. Stages only the exact task paths using explicit path arguments.
2. Confirms there are no unstaged tracked changes.
3. Computes the staged candidate fingerprint with:

   `git diff --cached --binary --full-index | git hash-object --stdin`

4. Freezes the staged candidate and runs the verification required by the
   delegated Addy Skills without editing or staging tracked files.
5. Recomputes the fingerprint after verification.
6. Commits only when verification is GREEN and both fingerprints match.

If verification fails, the Default may return internally to Build, make the
fix, restage the exact allowlist, compute a new fingerprint, and re-run
verification. It does not involve the Root unless Root-owned input is required.

## Default Reports

A successful checkpoint report contains:

- Result: GREEN.
- The checkpoint and completed tasks.
- The task branch name.
- The recorded original branch and base HEAD for every repository in scope.
- The created commit IDs.
- The committed paths for each task.
- Verification evidence required by the delegated Addy Skills.
- Candidate fingerprints before and after verification.
- Remaining staged and unstaged tracked paths.
- Known risks, or `None`.

The Default does not send progress updates or full logs unless needed to
explain a failure.

A Root escalation contains:

- The exact blocking condition.
- Why a Root decision, new authority, or external state is required.
- Relevant attempts already made.
- Available options and their tradeoffs.
- The specific decision required.
- Current branches, HEADs, commits, staged paths, unstaged tracked paths, and
  candidate fingerprints.

Root escalation is required only when resolution would change approved
requirements, scope, architecture, interfaces, acceptance criteria, or release
behavior; require new authorization; encounter unrelated or unexpected
repository state; or depend on unavailable external or user-only state.

## Review Routing

After a checkpoint completes, the Root creates a fresh Reviewer to independently
review the approved artifacts and checkpoint commits. The Reviewer follows the
applicable Addy Review Skills internally.

The Reviewer returns one verdict:

- **Pass:** no actionable findings remain.
- **Implementation findings:** fixes remain within approved scope.
- **Root escalation:** resolution requires a Root-owned decision, revised
  artifact, new authorization, or unavailable external state.

The Reviewer reports only to the Root and must not edit files, stage changes,
commit, merge, or perform Ship actions.

For implementation findings, the Root creates a fresh Default to complete Fix,
Re-verify, candidate-integrity checks, and verified local commits in one
delegation. The Root then creates a fresh Reviewer for Re-review.

Continue automatically until Review passes or Root escalation is required.

## Git and Submodules

The task branch name is fixed as `codex/<kebab-case-work-name>`.

During the first preflight, the Default records the original branch and HEAD
for the parent repository and every repository in scope. The original branch is
the task branch's base and final merge target.

After confirming the repository is clean, the first Default creates the
ordinary task branch. Subsequent fresh Defaults reuse the same task branch for
later checkpoints and fixes. Defaults must not implement changes directly on
the original branch.

Every modified submodule uses the same task branch name as the parent
repository. The Default creates or reuses each submodule task branch only after
confirming its original branch, expected base HEAD, and clean working state.

If a repository is in detached HEAD state, its original branch cannot be
resolved, or the task branch already exists at an unexpected state, the Default
stops and escalates to the Root. It must not reset, overwrite, rename, or delete
the branch.

Commit verified submodule changes before committing the parent repository's
submodule pointer.

When merging task branches, the Root first merges each modified submodule task
branch into its recorded original branch, then merges the parent repository's
task branch into its recorded original branch.

After all corresponding merges succeed, the Root deletes the task branches
from modified submodules first and the parent repository last.

## Ship

Ship requires explicit user authorization after final Review and is performed
only by the Root.
